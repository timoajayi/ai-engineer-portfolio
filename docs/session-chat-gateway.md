# Disabled secure Next.js session-chat gateway

Public chat and session issuance remain disabled by default. The chatbot UI now
uses only the same-origin session and chat gateways. A compact verification widget
provides a single-use proof; issuance sets the HttpOnly cookie without exposing its
token to JavaScript. Send, Enter and suggestions share this flow, with no automatic
retries. Closing clears unused proof; New chat keeps the existing session. Missing
or rejected sessions require verification again. No legacy destination is used.

## Verified backend contract

The backend implements `/internal/session-chat` in an outer, disabled ASGI adapter,
not a FastAPI/OpenAPI route. Exact `SESSION_CHAT_HTTP_ENABLED=true` is necessary
but insufficient there: startup also needs trusted pipeline/resolver composition.
Stage 1 now supplies narrowly scoped Vercel/Render production composition; see
[production integration](production-integration.md). It remains unverified on the
actual hosting platforms. The backend's current
production policy denies legacy `/chat`; authenticated legacy access is limited to
explicit isolated staging and cannot coexist with session HTTP enablement.

The frontend now constructs only this upstream request:

```text
POST <configured-backend-origin>/internal/session-chat
Authorization: Bearer <dedicated session-chat credential>
X-Portfolio-Session: <canonical token from the HttpOnly cookie>
X-Portfolio-Gateway-Assertion: <portfolio-gateway-assertion-v1>
Content-Type: application/json

{"message":"..."}
```

There is no legacy `/chat` destination, credential fallback, session creation or
request-ID header. Only these four explicit headers are created. Browser Origin,
Cookie, Authorization, forwarded IPs, arbitrary headers and identity claims never
become backend headers. Ordinary fetch transport headers such as Host and byte
length are generated by the HTTP implementation, not copied from the browser.

## Configuration and flags

All fields below are server-only, never `NEXT_PUBLIC_` values. No actual environment
file is read or changed during implementation/testing.

| Setting | Contract |
| --- | --- |
| `CHAT_ENABLED` | Only exact `true` opts in; leave absent/false. |
| `APP_ORIGIN` | Explicit HTTPS browser origin; no paths, credentials or wildcards. |
| `AI_ASSISTANT_BACKEND_URL` | Backend origin only; HTTPS except explicit loopback HTTP for local server testing. |
| `AI_ASSISTANT_CHAT_TOKEN` | Dedicated URL-safe 43–256-character backend `SESSION_CHAT_AUTH_TOKEN`. Required; no fallback. |
| `AI_ASSISTANT_BACKEND_TOKEN` | Existing session-issuance credential; comparison only in chat to reject equality. It must map to backend verified-session issuance scope for that separate gateway. |
| `GATEWAY_ASSERTION_ISSUER` | Exact backend-configured gateway issuer. |
| `GATEWAY_ASSERTION_AUDIENCE` | Exact backend audience. |
| `GATEWAY_ASSERTION_KEY_ID` | Configured current key ID, matching the backend authority/key ring. |
| `GATEWAY_ASSERTION_KEY` | Canonical unpadded base64url encoding of 32–64 independent CSPRNG key bytes. Secret. |
| `GATEWAY_ASSERTION_KEY_NOT_BEFORE` | Canonical decimal integer UTC Unix seconds. |
| `GATEWAY_ASSERTION_KEY_NOT_AFTER` | Canonical decimal integer UTC Unix seconds. |
| `GATEWAY_INGRESS_POLICY` | Exact approved ingress-policy identifier, matching provider and backend authority/resolver. |

`CHAT_SESSION_ENABLED` remains independent and unchanged. Changing either flag
does not enable the other. Equal chat/issuance credentials and obvious signing-key
reuse fail closed. Backend scoped configuration independently rejects equal
credentials. Operators must also keep signing keys separate from legacy staging,
IP-rate HMAC and Gemini secrets, even when those values are not known here.

The production route now supplies identity only under the fixed Vercel production
policy described in `production-integration.md`. Flags and keys alone are still
insufficient outside that platform runtime. No environment selector can select a
test identity. Public flags remain disabled and hosting verification is pending.

## Browser and session boundary

The handler requires POST, its exact configured origin/URL, an exact matching
Origin header, and the existing Fetch Metadata policy: if present, site is
`same-origin`, mode is `cors`/`same-origin`, destination is `empty`. Missing Origin,
cross-origin requests, queries and unexpected paths fail closed. Optional absence
of Fetch Metadata retains existing browser compatibility; Origin remains mandatory.

Only JSON/optional UTF-8 charset is accepted. Compression, Transfer-Encoding,
trailers, ambiguous Content-Length, duplicate decoded JSON keys, unknown/nested
fields, malformed UTF-8/BOM and lone surrogates are rejected. Message validation
retains Python-compatible whitespace trimming and counts Unicode codepoints before
trimming, with a maximum of 1,000. Raw upload is capped at 8,192 bytes and headers
at 32 entries/8,192 combined characters; body limits are enforced while streaming,
not solely by Content-Length. Declared byte lengths must match actual bytes.

Browser Authorization, internal session/assertion headers and recognizable forwarded
identity headers are rejected. Other benign headers are not forwarded. Web Headers
may combine duplicate wire headers; combined critical values are rejected. Actual
hosting/HTTP-parser behavior still requires integration validation.

The cookie is `__Host-portfolio-chat`, issued separately by the existing session
gateway with Secure, HttpOnly, SameSite=Strict, Path=/, no Domain and absolute
Expires no later than backend expiration. Chat only reads it server-side; it never
sets, refreshes, extends, decodes an expiry from, or returns it. Exactly one
canonical unpadded 43-character/32-byte token is required. Missing, malformed,
quoted, encoded or duplicate session cookies fail without upstream work.
Cookie attributes cannot be reconstructed from a request Cookie header; browser
`__Host-`/Secure enforcement and the existing issuer establish that boundary.
HTTPS is required for browser testing; no insecure development cookie is added.
The backend remains authoritative for revocation, verification and expiration.

## Identity and signing

`TrustedVisitorIdentityProvider` is an injectable, server-only abstract class.
There is no default implementation. Its private brand and base authorization method
reject plain objects, forged prototype objects and mismatched policy. Providers
receive a frozen context containing a fresh server request UUID, origin/method/path
and body/session digests—not raw cookies, credentials, session text or Request
headers. The UUID is never forwarded to the backend.

A trusted provider must independently establish ingress provenance and return a
canonical IP plus the approved policy, an evidence identifier and the matching
request UUID. The evidence record is an internal contract, not a new signature
protocol or an assertion that a named header is authentic. Matching fields alone
cannot prove real hosting provenance. Trusted composition and the provider's actual
evidence verification are part of the trusted computing base. A malicious in-process
provider/code execution is outside this boundary. No provider account or external
verification call is introduced.

Tests use explicit synthetic evidence only. No source IP is hardcoded in production
composition; browser headers/framework metadata never supply it automatically.
Invalid/noncanonical addresses, old request evidence, policy mismatch, provider
failure or absent provider fail closed. Future hosting work must establish a real
independent evidence source and revise forwarded-header handling only after review.

After browser validation the gateway serializes `{message}` exactly once into its
owned UTF-8 buffer. That same buffer is hashed by the existing signer and passed
to fetch. The existing v1 HMAC-SHA256 protocol, exact session-text hash, method/path,
issuer/audience/key ID, canonical IP and ingress policy are preserved. The lifetime
is 30 seconds and every deliberate request gets a fresh CSPRNG 32-byte nonce.
Signing-key windows are enforced. Key rotation must coordinate the backend ring
and authority; previous keys are verification-only there. Per-request signer copies
are destroyed in finally; JavaScript cannot guarantee erasure of all memory copies.

A valid signature authenticates the gateway's statement. It does not prove visitor-IP
provenance, session validity or human verification. The backend independently enforces
resolver authorization, durable replay, session/IP/global limits, emergency disable
and provider accounting. This phase modifies no backend source or data.

## Timeouts, responses and retries

Existing stage caps remain: upload 5 seconds, backend headers/body 45 seconds.
An additional absolute monotonic budget starts at handler entry and is at most
50 seconds (the sum of stage limits by default), including identity/signing and
response preparation. Every stage is capped by the remaining total. AbortController
signals propagate to fetch and stream readers; timers/listeners are cleaned up.
Noncooperative identity/fetch/streams cannot hold the browser response indefinitely,
and late identity completion cannot start an upstream request after cancellation.
The route's 55-second hosting hint is not a guarantee from a deployment platform.

The backend has its own 40-second deadline starting on backend entry; monotonic
clocks are not shared across hosts. Assertion timestamps use synchronized UTC
wall clocks: backend permits at most five seconds future skew and no expiry grace.
Admission must reach the backend before assertion expiry; already-admitted execution
may finish later. Network delays/clock error can cause safe rejection. Aborting
frontend fetch does not prove the remote synchronous Gemini call stopped.

Only HTTP 200 with strict UTF-8 JSON containing exactly one nonempty string
`answer` is accepted. Response bytes are capped at 65,536, including streamed bodies.
Redirects, unexpected encodings/schema/duplicate keys and raw backend errors are
never relayed. Known session/credential/assertion echoes in answer text are rejected
as an accidental-leak safeguard, not comprehensive protection against a compromised
backend. Browser responses have no-store and contain only answer or a generic detail;
no upstream cookies, headers, tokens, evidence or metadata are forwarded or logged.
Backend 429/503 map to safe 503, 504 to 504, other upstream failures to 502.
A locally missing/malformed cookie is 401; backend auth failures do not request
browser credentials.

There is exactly one fetch attempt, no redirect following, no retry and no legacy
fallback. A lost response never triggers another execution. A later explicit browser
submission is a new request with a new nonce and may consume another admission;
this is not exactly-once delivery across repeated user submissions. Backend replay
claims/accounting are not refunded after timeout or cancellation.
